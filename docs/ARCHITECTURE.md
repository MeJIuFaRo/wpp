# Устройство WPP в Docker

Как панель [web-panel-proxy](https://github.com/POLESNIESOVETI12/web-panel-proxy) 2.3.6, рассчитанная на установку на чистый VPS через systemd, работает в наборе контейнеров без изменения логики панели.

## Контейнеры

| Сервис | Образ | Что внутри | Наружу |
|---|---|---|---|
| `net` | `wpp-relay` (`sleep infinity`) | владелец сетевого пространства | 80/tcp, 443/tcp, 8443/tcp, 8443/udp |
| `caddy` | `caddy:2.11.4` | HTTPS, Let's Encrypt, маршруты панели и VLESS | — |
| `panel` | `wpp-panel` | панель, менеджер клиентов, периодические задачи | — |
| `relay` | `wpp-relay` | WEB-relay (tproxy-server) | — |
| `backends` | `wpp-mtproxy` | MTProxy: основной WEB-backend и backend каждого WEB-клиента | — |
| `mtproto` | `wpp-mtproxy` | общий MTProxy на 8443, до 64 ключей | — |
| `xray` | `wpp-xray` | VLESS XHTTP (за Caddy) и Hysteria2 | — |
| `openflux` | `wpp-openflux` | OpenFlux | — |

```
               80/443 tcp   8443 tcp   8443 udp
                    │           │          │
  ┌─────────────────▼───────────▼──────────▼─────────────────┐
  │ сетевое пространство контейнера net (как pod)            │
  │                                                          │
  │  caddy ──► relay :8080 ──► backends :2398, :2399…        │
  │    │  └──► panel :8090        mtproto :8443              │
  │    └─────► xray :10000        xray :8443/udp             │
  │                                                          │
  │  агенты служб на 127.0.0.1:9100–9105                     │
  └──────────────────────────────────────────────────────────┘
            ./config и ./data рядом с docker-compose.yaml
```

### Почему одно сетевое пространство

tproxy-server принимает публичные запросы только с loopback-адреса (через Caddy), а backend'ы и admin API тоже должны быть на loopback. Чтобы не ослаблять эти проверки, все контейнеры подключены к сети контейнера `net` (`network_mode: service:net`). Адреса 127.0.0.1 работают так же, как на VPS. Порты публикует только `net`; backend'ы и служебные порты снаружи недоступны.

`net` только держит сетевое пространство и ничего не делает, поэтому не перезапускается вместе с остальными службами.

## Управление службами без systemd

Панель пишет unit-файлы и вызывает `systemctl`/`journalctl`, как на VPS. В Docker это обслуживают два компонента:

- **Агент** (`src/agent/wpp_agent.py`) работает в каждом контейнере и запускает процессы по unit-файлам. Он поддерживает `ExecStart`, `Environment`, `EnvironmentFile`, `Restart`, `RestartSec`, `ConditionPathExists`, `Type=oneshot` и таймеры, хранит последние строки логов, помнит включённые службы. API — только на 127.0.0.1, с токеном из `config/control/agent.token`.
- **Замена `systemctl`/`journalctl`** в контейнере панели (`src/panel/bin/wpp-systemctl`). Она определяет по имени unit, какому агенту он принадлежит, и передаёт команду ему. Caddy агента не имеет: он сам применяет изменения Caddyfile (`caddy run --watch`).

Статические unit-файлы лежат в образах (`images/*/units`), динамические (клиенты WEB, общий MTProto, OpenFlux) панель пишет в `config/units`.

Первый запуск выполняет `wpp-init` в контейнере панели: создаёт конфигурацию relay, MTProxy, Caddy, данные панели и пароль администратора. Токен агентов создаётся последним: остальные контейнеры ждут его, поэтому стартуют службы только после появления конфигурации.

## Без root, без nftables и UFW

- Все контейнеры работают от UID/GID 10000, без capabilities (Caddy — только `NET_BIND_SERVICE`), с файловой системой только для чтения.
- Имена служебных пользователей VPS (`tproxy`, `xray`, `caddy`, `mtproxy`, `wpp-openflux`) в образе панели указывают на тот же UID; вызовы `chown(…, 0, …)` в панели заменены на текущего пользователя.
- nftables на VPS закрывал backend-порты и считал трафик. Закрывать порты в Docker не нужно: они не публикуются. Трафик считают сами службы (см. ниже).
- Обновление из панели отключено: образы обновляются через `docker compose pull && docker compose up -d`.

## Учёт трафика

| Что | Источник |
|---|---|
| WEB-клиент и основной WEB Proxy | счётчики байт по профилям в relay (`/metrics`, патч `relay 0002`) |
| MTProto-клиент | счётчики байт по ключу в общем MTProxy (`/stats`, патч `mtproxy 0003`) |
| MTProto всего по порту 8443 | счётчики клиентских соединений MTProxy (патч `mtproxy 0002`) |
| VLESS, Hysteria2 | Stats API Xray (как в 2.3.6) |

MTProxy считает байты на уровне клиентских сокетов: трафик до серверов Telegram в учёт не попадает. Байты, прочитанные до того, как стал известен ключ клиента, относятся к ключу, когда он определён. Счётчики ключа в `/stats` подписаны первыми 8 байтами SHA-256 ключа, а не самим ключом; `/stats` отвечает только запросам с 127.0.0.1.

Счётчики служб живут, пока жив процесс. Панель хранит накопленный трафик в `data/panel/traffic.json` и прибавляет разницу каждые 10 секунд. Уменьшение показания считается перезапуском процесса. При перезапуске общей MTProto-службы (добавление или отключение MTProto-клиента) теряется трафик с последнего замера.

## MTProxy за NAT Docker

MTProxy сообщает серверам Telegram свой адрес при RPC-рукопожатии. Внутри контейнера он видит только адрес контейнера, рукопожатие не проходит, и MTProxy переподключается тысячи раз в секунду. На небольшом VPS это может переполнить таблицу conntrack ядра.

Поэтому путь `/opt/MTProxy/objs/bin/mtproto-proxy` в образе — обёртка (`images/mtproxy/mtproto-proxy-wrapper`). Она добавляет `--nat-info <адрес контейнера>:<публичный IPv4>`. Публичный адрес берётся из `WPP_PUBLIC_IP` или определяется через api.ipify.org (как в установщике 2.3.6).

## Доработки относительно 2.3.6

| Компонент | Изменение |
|---|---|
| relay 0001 | горячее перечитывание профилей (`POST /profiles/reload`): новый WEB-клиент добавляется без перезапуска relay и чужих сессий |
| relay 0002 | счётчики байт по профилям в `/metrics` |
| MTProxy 0001 | до 64 ключей в одном процессе (было 16) |
| MTProxy 0002 | счётчики байт клиентских соединений в `/stats` (`--http-stats`) |
| MTProxy 0003 | счётчики байт по каждому ключу |
| панель | общий MTProto на 8443; лимит профилей 128 (relay и панель); ожидание готовности backend; горячее добавление WEB-клиента; учёт трафика по службам; MTProto-клиенты с собственным трафиком в интерфейсе; Docker-версии служебных скриптов |

Исходники upstream закреплены по коммитам и контрольным суммам (`versions.env`). Патчи relay и MTProxy применяются к ним при сборке; код панели хранится целиком в `src/panel`, состояние до переноса в Docker — в `reference/2.3.6/panel`.

## Проверки

- `tests/smoke-relay.sh` — relay и агент: здоровье, перезапуск через API, логи, отказ без токена, UID.
- `tests/smoke-mtproxy.sh` — реальный обмен MTProto с Telegram по двум ключам, точность общих счётчиков и счётчиков по ключам, ключи не попадают в `/stats`.
- `tests/integration.sh` — весь стек без публичного домена: первый запуск, WEB-клиент без перезапуска relay, MTProto на 8443 и его трафик, перезапуск стека с сохранением клиентов, удаление клиента.
- `tests/e2e-public.py` — на развёрнутом сервере через публичный домен и сертификат: WEB Proxy (сессия не рвётся при добавлении клиента), MTProto, трафик, VLESS, Hysteria2.

## Ограничения

- Удаление и отключение WEB-клиента, как в 2.3.6, перезапускают все WEB-службы; без разрыва соединений работает только добавление.
- Изменение набора MTProto-ключей перезапускает общую MTProto-службу.
- Клиенты подписок без заголовка `X-HWID` (например, Hiddify) работают только с подписками без лимита устройств (лимит 0).
- Только x86_64.
